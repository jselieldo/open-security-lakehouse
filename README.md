# Open Security Lakehouse

Milestone 11 introduces a source-coverage catalog, Docker container lifecycle
collection, investigation filters for hostname/application/event type, and a Docker
failure rule. Onboarding is staged; vendor-specific firewall/router and application
parsers require sanitized real samples. See
[the source onboarding runbook](docs/runbooks/milestone11-sources.md).
**Back up the running homelab before applying migration `0003_source_catalog`.**

Milestone 10 added a dedicated detection worker, Alertmanager and alert triage.
Prometheus and Grafana provide ingestion, dependency and lake metrics.

This is a development foundation, not a production-ready SIEM. The Compose topology is single-host and has no high availability or TLS termination.

## Prerequisites

- Native Linux (x86_64 or arm64)
- Docker Engine 24+ with Docker Compose v2
- GNU Make, curl, and OpenSSL
- Python 3.12+ only when running tests outside containers
- Recommended: 4 CPU cores, 16 GB RAM, and 20 GB free disk

## Install and start

```bash
git clone <repository-url> open-security-lakehouse
cd open-security-lakehouse
cp .env.example .env
```

Edit `.env`. Replace every `CHANGE_ME` value. Generate secrets, for example:

```bash
openssl rand -hex 32
```

Validate and start:

```bash
docker compose config --quiet
docker compose up --build --wait
docker compose ps
```

The API and Keycloak are exposed on loopback at `http://127.0.0.1:8000` and `http://127.0.0.1:8080`. PostgreSQL and SeaweedFS remain private.

## Collect Linux/syslog events

Vector 0.61.0 listens for RFC 3164/5424 syslog over TCP on port 5514. Restrict `SYSLOG_ALLOWED_CIDR` in `.env` to the homelab subnet before starting. UDP is intentionally disabled because it cannot provide delivery feedback.

For the homelab host itself, install the versioned selective forwarding policy:

```bash
./scripts/install-homelab-autocollection.sh
```

It forwards authentication events and warning-or-higher kernel/daemon events over TCP with a persistent queue. Test messages generated by `milestone7-smoke-test.sh` are stored under `test-syslog`; operational host events use `linux-syslog`. Detection rules can therefore exclude synthetic and smoke-test sources.

Verify the path:

```bash
sudo systemctl restart rsyslog
logger -p auth.warning "OSL syslog validation"
./scripts/milestone7-smoke-test.sh
```

Vector stores pending delivery data in the `vector-data` volume. Its dedicated bearer credential maps to an `ingestor`-only machine principal; it cannot read investigations, alerts, users, or audit logs. The `/api/v1/ingestion/vector` adapter generates deterministic batch and event identifiers so HTTP retries remain idempotent.

## Observe the platform

Prometheus is available on `http://127.0.0.1:9090` and Grafana on `http://127.0.0.1:3000`. From another computer, add both ports to the SSH tunnel:

```bash
ssh \
  -L 8000:127.0.0.1:8000 \
  -L 8080:127.0.0.1:8080 \
  -L 9090:127.0.0.1:9090 \
  -L 3000:127.0.0.1:3000 \
  homelab-lan
```

Sign in to Grafana with `GRAFANA_ADMIN_USER` and `GRAFANA_ADMIN_PASSWORD` from the homelab `.env`. The **OSL / Open Security Lakehouse — Operações** dashboard and Prometheus datasource are provisioned from Git and are read-only in the UI.

Prometheus retains up to 15 days or 2 GB, whichever is reached first. Initial alert rules cover API/Vector availability, PostgreSQL or S3 readiness, failed ingestion, high quarantine ratio, storage-metric refresh failures, and Vector event drops.

Alertmanager is available on `http://127.0.0.1:9093`. It receives platform alerts from Prometheus and keeps their grouping and lifecycle visible locally. Configure an external receiver in `infrastructure/alertmanager/alertmanager.yml` when a delivery destination is chosen.

## Identity, roles, and audit

The installation creates two local test identities from `.env`: an analyst with `viewer`, `ingestor`, and `analyst` roles, and an administrator with `admin`. Change these credentials before first start.

| Role | Access |
| --- | --- |
| `viewer` | dashboards, batches, rules, alerts, and investigations |
| `ingestor` | event ingestion and batch status |
| `analyst` | investigations and detection execution |
| `admin` | all operations and audit-log access |

Tokens are verified with the realm's published signing keys plus strict issuer and audience checks. Successful authenticated requests and authorization denials are recorded in PostgreSQL. The `GET /api/v1/users/me` endpoint returns the current identity; `GET /api/v1/audit` is admin-only.

For an existing installation, set `AUTH_MODE=hybrid`, deploy once, confirm OIDC with `milestone6-smoke-test.sh`, then change it to `oidc` and recreate the API. New and upgraded deployments run `alembic upgrade head` before the API starts. To inspect migration state:

```bash
docker compose exec api alembic current
docker compose exec api alembic history
```

## Ingest the first events

Load the local environment and send a mixed synthetic batch:

```bash
set -a; source .env; set +a
./scripts/ingest-synthetic.sh --count 10 --invalid 1
```

The authenticated `POST /api/v1/ingestion/batches` endpoint stores the original JSON batch under `raw/`, writes valid normalized rows as Zstandard-compressed Parquet under `normalized/`, and writes invalid events with validation errors under `quarantine/invalid-events/`. Reusing the same `batch_id` and source returns the persisted result without writing duplicate objects.

Retrieve batch state with:

```bash
TOKEN="$(./scripts/get-access-token.sh)"
curl --fail -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8000/api/v1/ingestion/batches/<batch-id>
```

## Investigate normalized events

Investigations accept structured filters only; clients cannot submit arbitrary SQL:

```bash
TOKEN="$(./scripts/get-access-token.sh)"
curl --fail \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data '{
    "src_ip": "198.51.100.42",
    "source": "synthetic-linux",
    "start_time": "2026-11-15T00:00:00Z",
    "min_severity": 2,
    "limit": 100
  }' \
  http://127.0.0.1:8000/api/v1/investigations/search
```

The API lists matching Parquet objects through the S3 contract, loads their Arrow tables, and executes a parameterized DuckDB query. The response includes scanned object count, duration, and matching events.

## Run detections and inspect alerts

Rules live under `detections/rules/` as reviewed YAML files. List and run them with:

```bash
TOKEN="$(./scripts/get-access-token.sh)"
curl --fail -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8000/api/v1/detections/rules

curl --fail -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8000/api/v1/detections/rules/high-severity-events/run

curl --fail -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8000/api/v1/alerts
```

Enabled rules run on their configured interval in the dedicated detection worker. Matching event identifiers form a deterministic alert fingerprint, preventing repeated runs from generating duplicate alerts. Full evidence is written under `artifacts/detection-evidence/` and the alert metadata is stored in PostgreSQL.

The bundled high-severity rule examines a moving 20-minute window and excludes `synthetic-linux` and `test-syslog`, so validation traffic does not create operational alerts. Additional rules detect repeated SSH authentication failures and privileged `sudo` commands.

Scheduled rules run in the dedicated `detection-worker`, isolated from API and console traffic. Security alerts support assignment, comments, and controlled transitions between open, investigating, resolved, false-positive, and reopened states. Every change is retained in the alert timeline.

To send newly created security alerts to another system, set an HTTP(S) endpoint in `.env` and recreate the worker:

```text
ALERT_WEBHOOK_URL=https://example.internal/hooks/osl
```

Webhook failures are recorded in PostgreSQL and never cancel the detection run.

## Open the web console

The console is available at `http://127.0.0.1:8000/console/`. From another computer, keep the API private and use an SSH tunnel:

```bash
ssh -L 8000:127.0.0.1:8000 -L 8080:127.0.0.1:8080 homelab-lan
```

Open `http://127.0.0.1:8000/console/`, choose **Entrar com OIDC**, and authenticate through Keycloak. The console uses Authorization Code with PKCE and keeps the access token only in browser `sessionStorage`.

## Operations

```bash
docker compose logs -f --tail=100
docker compose down                 # preserve named volumes
docker compose down --volumes       # destructive: delete all local platform data
```

Back up the named volumes before upgrades. Do not expose ports 8000 or 8080 publicly without TLS termination, hardened Keycloak production settings, rate limiting, and trusted hostname configuration. `start-dev` is appropriate only for this loopback homelab topology.

## Backup and recovery drill

Create a backup key once, outside the repository, then run an encrypted backup:

```bash
mkdir -p "$HOME/.config/osl" "$HOME/osl-backups"
openssl rand -base64 48 > "$HOME/.config/osl/backup.key"
chmod 600 "$HOME/.config/osl/backup.key"
./scripts/backup.sh
```

The archive contains custom-format dumps for the OSL and Keycloak PostgreSQL databases, an object-by-object lake export, a consistent Grafana volume snapshot, `.env`, Compose configuration, Git revision, and SHA-256 manifest. AES-256-CBC with PBKDF2 encrypts the archive; the key is never included. Backups older than 14 days are removed by default.

Test a backup without overwriting production data:

```bash
./scripts/verify-backup.sh "$HOME/osl-backups/<backup>.tar.enc"
```

The drill checks both integrity layers, restores both databases under temporary names, validates Grafana SQLite, restores the lake under an isolated temporary prefix, compares object counts and bytes, then removes all temporary resources. See [the recovery runbook](docs/runbooks/backup-restore.md) for scheduling, off-host copies, and full disaster recovery.
